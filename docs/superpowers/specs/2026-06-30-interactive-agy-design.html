Overview

This spec defines the agy-specific seam of the interactive adapter framework. The shared mechanism (mailbox, doorbell, session harvesting, state machine) is defined in the canonical interactive-codex-design.md frame. This document fills only the per-CLI profile: launch argv, env isolation, instruction file, submit key, session directory, and harvest logic.

Verified Profile

All fields verified via terminal-probe.test.ts (`TERMINAL_PROBE=1`, passed 2026-07-01):

Launch argv

agy --dangerously-skip-permissions --new-project [--model M] --add-dir <cwd>

Note: --sandbox intentionally omitted — unverified mapping between InteractiveOpts.sandbox (3-way enum) and agy's boolean switch. No approved mapping exists.

Env isolation & instruction channel

  • HOME env var relocates config/session dir (same pattern as one-shot adapter)
  • Instruction file: GEMINI.md (read by agy as instructions on launch)

Submit sequence & session handling

  • Submit key: plain Enter ("\r") — original skeleton guessed kitty escape; probe disproved it
  • No on-disk session transcript: agy does not persist a readable session rollout/JSONL (unlike codex)
  • Session metadata fallback: sessionInfoPrompt asks the agent to write outbox/session-info.json with conversationId, which becomes the harvested sessionId. Prompt text is Vietnamese (probe-tested wording).
  • Session dir: ~/.gemini (default) or {configDir}/.gemini (when isolated)

Known limitation: degraded mode

Because agy does not expose a readable on-disk session transcript (unlike codex's rollout JSONL), the interactive session runs without automatic token/usage reporting. The turn boundary still works (the agent writes outbox/turn-N.json per the shared contract), but harvested metadata is unavailable. This mirrors the existing one-shot agy adapter, which already stubs usage.

The file-based mailbox protocol is what makes interactive agy viable at all — it sidesteps the original weakness of --print plain-text scraping.

Out of scope (inherited from frame)

  • Multi-worker fleet / scheduler (v1 has single workerId per session)
  • Claude / other CLI interactive profiles (separate skeleton specs)
  • Automated crash/timeout recovery via resume
  • Windows child-PID polling (macOS/Linux only in v1)
