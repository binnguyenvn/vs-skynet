Codex Adapter — Design

Adapters (subsystem 1) · the first, concrete CLI bridge — built and proven on its own.

2026-06-29 codex-cli 0.142.3 parent: skynet-vision-design

Goal

A standalone, concrete bridge that runs a task through the codex CLI and turns its output into a typed, observable stream with a clear terminal status. This is the first adapter.

Bottom-up by decision. Build each CLI adapter concrete and working first (codex → claude → agy). Do not invent a shared AgentAdapter interface or normalized WorkerEvent type yet — that abstraction is extracted in a later US once ≥2 real adapters exist and the genuine commonality is visible. Premature abstraction from one example is what we're avoiding.

Scope is codex only. No fallback/retry (Decision A), no step-function panel (subsystem 2), no shared types.

Verified ground truth (real CLI)

codex-cli 0.142.3. The adapter drives the non-interactive path:

codex exec --json --skip-git-repo-check -s read-only -C <cwd> [-m <model>] "<prompt>"

--json prints events to stdout as JSONL. A real "reply pong" run emitted:

{"type":"thread.started","thread_id":"019f..."}
{"type":"turn.started"}
{"type":"item.completed","item":{"id":"item_0","type":"agent_message","text":"pong"}}
{"type":"turn.completed","usage":{"input_tokens":12406,"cached_input_tokens":9088,"output_tokens":5,"reasoning_output_tokens":0}}
Gotcha (observed): when stdin is an open/empty pipe, codex prints "Reading additional input from stdin..." and blocks. The adapter MUST pass the prompt as an argv argument and set the child's stdin to 'ignore'.

Run strategy chosen: spawn codex exec --json and parse JSONL. Rejected — app-server/mcp-server (experimental, heavier) and plain-text stdout scraping (fragile).

Public shape (concrete, codex-specific)

New directory src/adapters/codex/, isolated from the webview.

type CodexEvent =
  | { kind: 'started'; threadId: string }
  | { kind: 'message'; text: string }
  | { kind: 'usage'; inputTokens; cachedInputTokens; outputTokens; reasoningOutputTokens }
  | { kind: 'unknown'; raw: unknown };   // forward-compat for new codex events

type CodexResult = {
  status: 'success' | 'failed' | 'cancelled';
  reason?: string;
  errorClass?: 'limit' | 'transport' | 'terminal';   // when status==='failed'
  usage?: CodexUsage;
  lastMessage?: string;
};

interface RunOpts { prompt; cwd; model?; sandbox? = 'read-only'; }
interface CodexRun extends AsyncIterable<CodexEvent> { cancel(): void; result: Promise<CodexResult>; }
function runCodex(opts: RunOpts): CodexRun;

unknown{raw} keeps the parser forward-compatible: an unmodeled codex event surfaces as unknown instead of crashing.

Data flow

  1. runCodex spawns the child (argv above, stdin:'ignore', piped stdout/stderr).
  2. stdout split on newlines; each line JSON.parsed and mapped: thread.started→started, item.completed(agent_message)→message, turn.completed→usage, else→unknown. Yielded as they arrive.
  3. stderr buffered (used only for error classification).
  4. On child exit/error the result promise resolves.

Error classification (heuristic — Phase-1 requirement)

Adapters classify failures so a future fallback layer has signal. The adapter does no retry.

classifyError(exitCode, stderr) — pure function matching stderr text:

  • /rate.?limit|429|quota|too many requests/i → limit
  • /network|econn|etimedout|timeout|socket|dns|enotfound/i → transport

Proof of function (acceptance gate)

No step-function panel yet, so proof is a real integration test (existing vscode-test/mocha) plus a fast unit test for the pure classifier.

  • happy (real codex, slow/uses quota): runCodex({prompt:"reply pong"}) → a message with pong, status==='success', usage present.
  • cancel (real codex, slow): start a longer task, .cancel() mid-run → status==='cancelled'.
  • classify (pure, fast): classifyError returns the right class for representative stderr strings.

Out of scope

  • Shared AgentAdapter / normalized WorkerEvent (later US, after ≥2 adapters).
  • Fallback/retry/AgentPool (Decision A — Orchestrator/Phase 2).
  • Step-function panel and observability (subsystem 2).
  • Soul injection, multi-turn/resume, images, output-schema (later USs).
