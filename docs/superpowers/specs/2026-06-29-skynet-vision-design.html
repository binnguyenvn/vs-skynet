Skynet — Product Vision (redesign)

North-star umbrella · the single source of truth for the whole extension.

2026-06-29 supersedes the 2026-06-26 vision + worker roadmap spec: docs/superpowers/specs/2026-06-29-skynet-vision-design.md

1. North star

A developer hands Skynet an idea; Skynet runs a disciplined delivery workflow as an orchestrated AI team — pausing only for the decisions a human must make — and returns a real, tested, reviewed product, not tech-debt. Worker = Agent + Harness + Soul stays the executor model. The redesign keeps that core; it changes the build order, makes provable operation a requirement of every layer, and promotes Tools/Plugins to its own subsystem.

2. Why this redesign

The previous plan built Codex-only, deep first. Two failures surfaced:

  1. Single-provider block — when the one Codex agent hit a rate limit, the whole dev/test loop stalled with nothing to fall back to.
  2. No visible proof — the harness test couldn't show whether the implementation actually worked; it just silently stopped.

3. Cross-cutting principles

P1 — Never blocked by one provider

Multiple CLI adapters (codex, claude, agy) are built first so no single provider's limit can block downstream work. In Phase 1 the adapter is selected and switched manually on a limit; automated fallback is a later (Orchestrator) concern — see Decision A.

P2 — Every layer proves itself

Each pre-MVP layer is accepted only by a real end-to-end run, against real CLIs, rendered live as a step-function state machine: each step shows Success / Failed / Cancelled / In-Progress. A hung or rate-limited step renders In-Progress → Failed — never a silent stall. The panel is a permanent product feature and doubles as each layer's acceptance proof.

5. Build order

Terminology (matches the roadmap): the build splits into two Phases — Phase 1 — MVP and Phase 2 — Post-MVP. In Phase 1 each subsystem = one Epic (Adapters, Harness, Soul, Tools/Plugins, Orchestrator). Phase 2's "Management" is not one Epic — it decomposes into several small Epics (Agent / Tool / Plugin / Identity Management, Multi-Account, AgentPool & Fallback, Persistence). Each Epic's capabilities are its Features.

Each subsystem ships something real and passes its step-function proof before the next begins.

4Tools / Plugins catalog of third-party packs; end-user Install runs them into the CLIs; the harness gates usage per task (installed ≠ always on). Install superpowers; task A (no tools) is denied it, task B (needs it) uses it — both visible.

6+Management (Phase 2, several Epics) Agent / Tool / Plugin / Identity Management (CRUD); Multi-Account; AgentPool & Fallback (the automated form of P1, deferred here by Decision A); Persistence (durable runs across restarts). —

6. The proof model (acceptance gate)

Every pre-MVP subsystem defines one small fixed scenario as a step-function. "Done" means the scenario runs against real CLIs and every step reaches a terminal state matching expectation — green for success, or a deliberately red step where the design calls for it (e.g. the verification gate rejecting a fake "done"). A hung or rate-limited run is visibly Failed, so "it silently stopped, did it even work?" can no longer happen. The panel that proves the layer is the panel that ships.

7. Key decisions

Decision A — adapters are dumb bridges; resilience is deferred. Adapters carry no fallback/retry logic. In Phase 1 a provider limit is worked around manually. Automated fallback (retry-next-adapter, later tier/round-robin AgentPool) lands with the Orchestrator / Management. Bought: clean single-responsibility adapters. Cost (on record): the limit-block pain is only manually mitigated until the Orchestrator — accepted. Adapters must still classify errors so the later fallback layer has the signal it needs.

9. Out of scope

Semantic auto-routing · cloud/remote execution · HTTP/cloud agents (CLI-only until after MVP) · cross-user collaboration · cross-provider billing/cost optimization.
